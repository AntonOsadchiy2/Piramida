# ПИРАМИДА: КАМЕНЬ ЗА КАМНЕМ
## Game Design Document + техническая спецификация

> Исходная спецификация замороженной Android-игры. [Мобильный архив](LEGACY_ANDROID.md)

**Версия:** 1.1 (адаптация под Godot 4.x)  
**Статус:** готово к прототипированию; значения баланса предварительные  
**Жанр:** 2D idle-management / производственная симуляция  
**Платформа:** Android, альбомная ориентация; Windows в редакторе для тестов  
**Движок:** Godot 4.x, GDScript 2.0, 2D (TileMapLayer / Sprite2D)  
**Модель:** одиночная, офлайн, без аккаунта, без рекламы и покупок в MVP

> **Принятое допущение.** Это самостоятельная первая игра с одной завершаемой пирамидой. Числа ниже являются начальными настройками для разработки, а не доказанным балансом. Все значения вынесены в данные и проверяются симуляционными тестами.

# 1. Концепция и продуктовые рамки

## 1.1. Игровая фантазия
Игрок руководит небольшой строительной площадкой. Каменотёс добывает глыбы в карьере, носильщики тащат их на волокушах за верёвку, обработчик придаёт им форму кирпичей, строитель по одному укладывает их в пирамиду. Карьер постепенно углубляется, пирамида растёт, а маршруты меняются. Задача игрока — своевременно увеличивать пропускную способность узких мест, пока производство не завершит сооружение.

**Главный визуальный принцип:** каждый из 900 установленных кирпичей соответствует одной реально добытой и обработанной глыбе. Ресурсы не возникают из ничего и не теряются.

## 1.2. Основная петля
1. Боты автоматически добывают, переносят, обрабатывают и устанавливают камень.
2. Установка кирпича приносит монеты, завершение ряда даёт бонус.
3. Игрок оценивает загрузку этапов и покупает улучшения или новых носильщиков.
4. Карьер уходит в глубину; новая геометрия меняет время доставки.
5. Игрок открывает все 30 рядов и завершает пирамиду.

**Активная игра:** наблюдение, переключение камеры, покупки и принятие решений об узких местах. **Idle:** производство идёт без нажатий и прогрессирует во время отсутствия игрока, без автоматических покупок.

## 1.3. Цели MVP
- Понятный цикл «глыба → доставка → кирпич → строительство» с анимацией.
- Визуально накапливаемый прогресс: 30 рядов, 900 кирпичей.
- Четыре роли, одна управляемая цепь запасов, 1–8 носильщиков.
- Минимум три осмысленных типа решений: скорость специалистов, скорость транспорта, количество/вместимость носильщиков.
- Стабильные сохранения и офлайн-прогресс до 4 часов.
- Целевой темп первого прохождения: приблизительно 60–120 минут активного/смешанного времени **после проверки балансом**.

## 1.4. Вне MVP
Престиж, строительство нескольких пирамид, исследование технологий, случайные катастрофы, ручное управление ботами, рыночная торговля, сложная физика, мультиплеер, реклама, IAP, процедурные карты, персональные навыки каждого носильщика. Архитектура не должна блокировать расширение, но функциональность не реализуется заранее.

# 2. Геометрия и правила мира

## 2.1. Система координат и вид
- Игра — **боковая 2D-проекция**. Камера смотрит на карьер слева и пирамиду справа.
- Логическая ось X направлена вправо, Y вверх. Земля около Y = 0.
- На экране видны: карьер, наклонная лестница-рампа на его ближнем краю, склад сырья, мастерская, склад кирпичей, подъёмник стройки, пирамида. Опорные X-координаты: ближний край карьера `0`, склад сырья `3`, мастерская `5`, склад кирпичей `7`, левый край основания пирамиды `9`. Карьер простирается от `0` влево на 18 ед., пирамида от `9` вправо на 21.24 ед.
- Боты двигаются по предопределённым путям в мире. Пиксельное совпадение ног и кирпичей доводится на этапе художественного прототипа; логические координаты не зависят от спрайтов.

## 2.2. Пирамида (фиксированная геометрия)
- 30 горизонтальных рядов, индексы `r = 0…29`, снизу вверх.
- В ряду `r`: **`B(r) = 59 - 2r`** кирпичей.
- Ряд 0 содержит 59 кирпичей, ряд 1 — 57, последний ряд 29 — 1.
- Итого **`Σ B(r) = 900`** кирпичей.
- Ширина кирпича в логических единицах `bw = 0.36`, высота `bh = 0.28`.
- Ряд центрируется относительно общей центральной оси. Левый край ряда: `pyramidLeft + r*bw`, позиция кирпича `j` (от 0): `x = pyramidLeft + (r+j)*bw`, `y = r*bh`.
- Следующий ряд доступен, только когда все кирпичи текущего ряда установлены.
- Строитель работает слева направо; одновременно устанавливается только один кирпич.
- После установки 900-го кирпича игра переходит в состояние завершения.

## 2.3. Карьер (фиксированная геометрия)
- **9 слоёв** по **100 глыб**: ровно 900 единиц сырья, без запасных камней и потерь.
- Пока `minedCount < 900`: `layer = floor(minedCount / 100)`, `index = minedCount % 100`; `minedCount` меняется только при завершении добычи. При `minedCount = 900` состояние `Exhausted`, расчёт следующей клетки не выполняется.
- Каждая новая глыба расположена дальше от пирамиды: `x = quarryNearEdge - (index + 0.5)*0.18` лог. ед.
- Высота поверхности рабочего слоя: `y = -layer*0.80`.
- Рабочий начинает слой возле ближнего края карьера и постепенно движется влево.
- После каждой сотой глыбы он **по рабочему маршруту возвращается** к ближнему краю, спускается по автоматически расширенной рампе на следующий слой и начинает с первой позиции. Мгновенного телепорта нет.
- Карьер имеет открытую сверху ступенчатую выемку. Под добываемой глыбой находится следующий слой породы, а не висящий в воздухе массив. Удалённые клетки визуально превращаются в пустое пространство; обрушений нет.
- На последнем, девятом слое, после 900-й глыбы добыча останавливается. Необработанные ресурсы ещё могут находиться в цепи.
- Неперенесённые глыбы предыдущих слоёв остаются доступными носильщикам после перехода каменотёса вниз.

## 2.4. Лестница и перевозка
- На ближней к пирамиде стенке карьера автоматически появляется **деревянная лестница-рампа**, когда добыча открывает очередной слой.
- Внешне это лестничные ступени с наклонными направляющими, по которым можно волочить груз. Каменотёс и носильщики ходят по ступеням; глыбы везутся на волокушах за верёвку. Поэтому подъём тяжёлой глыбы по конструкции не выглядит невозможным.
- Рампа находится на заднем визуальном плане, **но входит в расчёт маршрута**.
- Длина пути от глыбы до склада сырья: `D = horizontalDistanceToNearEdge + rampLength(layer) + nearEdgeToRawStorage`.
- `rampLength(layer) = layer*1.20`; `nearEdgeToRawStorage = 3.0` лог. ед.
- При спуске/подъёме груза скорость та же базовая, что на земле. Отдельный штраф на уклон в MVP не нужен; расстояние рампы уже учитывается.

## 2.5. Строительные леса и подъёмник
- Строительная площадка имеет **автоматический канатный подъёмник** слева от активного ряда. Это логический механизм без отдельного рабочего.
- Он переносит по **одному** готовому кирпичу со склада на площадку активного ряда; на площадке хранится до **6** кирпичей.
- Время одного подъёма: `T_lift(r) = 1.5 + 0.15*r` секунд, где `r` — номер ряда.
- После завершения ряда подъёмник и строительные леса автоматически перестраиваются под следующий ряд, уже доставленные на площадку кирпичи сохраняются.
- Площадка ряда находится на `x = 9 + r*0.36 - 0.8`, `y = r*0.28`. Строитель забирает кирпич с площадки, идёт по лесам до позиции следующего кирпича, устанавливает его и возвращается к площадке за следующим. Перемещения рассчитываются по расстоянию/скорости, без штрафов за ожидание анимации.
- Строитель и кирпич физически следуют по лесам (вычисляемому маршруту), а не проходят сквозь пирамиду. В MVP используются линейные участки с вертикальным подъёмом на площадку.

# 3. Материалы, склады и непрерывность цепочки

## 3.1. Единственный материал
Одна добытая глыба → одна доставленная глыба → один обработанный кирпич → один установленный кирпич. Потерь, отходов, случайных результатов и бонусной генерации в MVP нет.

## 3.2. Узлы производства
| Узел | Вход | Выход | Ёмкость | Условие остановки |
|---|---|---|---:|---|
| Карьер | нет | готовая к вывозу глыба | 15 глыб в карьере | очередь глыб заполнена или ресурс исчерпан |
| Носильщики | глыбы в карьере | сырьё на складе | 1–4 на волокуши | нет задач или свободных зарезервированных мест на складе |
| Склад сырья | от носильщиков | в обработку | 30 | заполнен |
| Мастерская | 1 глыба | 1 кирпич | 1 в работе | нет сырья или склад кирпичей не может принять результат |
| Склад кирпичей | от мастерской | в подъёмник | 30 | заполнен |
| Подъёмник | 1 кирпич | площадка | 1 в пути | нет кирпичей или мест на площадке |
| Площадка ряда | от подъёмника | в руки строителя | 6 | заполнена |
| Строитель | 1 кирпич | установленный кирпич | 1 в руках | нет кирпича на площадке или пирамида готова |

**Примечание:** груз, находящийся у носильщика, в мастерской, подъёмнике или в руках строителя, учтён ровно в одном состоянии; инвентарь не дублируется между складами.

## 3.3. Защита от конфликтов
- Глыба обладает уникальным `resourceId` (0…899) и статусом `Ready`, `Reserved`, `InTransit` или далее по цепи.
- Перед выходом носильщик атомарно резервирует конкретные готовые глыбы и равное число свободных слотов склада сырья. Резервация склада считается занятой до разгрузки.
- Критерий выбора партии: ближайшие к носильщику доступные глыбы **одного слоя карьера**; при равенстве — меньший `resourceId`. Вместимость позволяет захватить несколько объектов, но один рейс ограничен ёмкостью волокуши. Если на слое осталось меньше глыб, чем вместимость, носильщик увозит неполную партию.
- В одном рейсе носильщик может подобрать несколько глыб на разных точках **одного слоя**. Он проходит выбранные точки по горизонтали в оптимальном для этих точек порядке; никакого физического «склеивания» глыб не требуется.
- При отказе/загрузке сохранения резервации реконструируются из состояния задач. Двойных захватов быть не должно.
- Мастерская резервирует выходной слот до начала цикла; подъёмник резервирует место на площадке до запуска; строитель забирает только реально доступный кирпич.
- Заполненный узел блокирует предыдущий, но не приводит к потере ресурса. Взаимная блокировка исключается направленностью цепи и резервированием места назначения.

# 4. Рабочие и машины состояний

## 4.1. Каменотёс (1 шт.)
**Задача:** последовательно открыть 900 клеток карьера. **Базовое время обработки:** 3.5 с за глыбу. **Скорость ходьбы:** 2.6 лог. ед./с.

Состояния: `Idle → MoveToCell → Mine (3.5 с / модификатор) → SpawnReadyStone → MoveToCell`; на индексе 99: `ReturnToNearEdge → DescendRamp → MoveToCell`. Остановка: заполнена очередь из 15 ещё не вывезенных глыб либо добыты все 900. Если очередь заполнена во время добычи, текущая обработка заканчивается, но следующая не начинается.

**Несколько каменотёсов в MVP не поддерживаются**: одна линия добычи, один исполнитель. Улучшается скорость одного специалиста, чтобы избежать коллизий и деления единого забоя.

## 4.2. Носильщики (1–8 шт.)
**Задача:** перемещать готовые глыбы из карьера на склад сырья. Начинается с **1** носильщика. **Скорость без груза:** 3.2 ед./с. **С грузом:** 2.8 ед./с. **Погрузка:** 0.5 с на глыбу. **Разгрузка:** 0.7 с на глыбу.

Состояния: `Idle → ReserveBatch → WalkToPickup → Load → (NextPickup | WalkToStorage) → Unload → Idle`.

- Вместимость волокуши изначально 1 глыба, улучшается до 4 для **всех** носильщиков.
- Рейс может начинаться, если есть хотя бы одна незарезервированная глыба и место на складе; заполнения волокуши ждать не требуется.
- Максимум 8 носильщиков. Они не сталкиваются друг с другом и могут проходить через одни и те же точки; визуально немного сдвигаются по Y для читаемости.
- Глыбы изображаются привязанными к волокуше; динамические предметы берутся из пула.

## 4.3. Кирпичник / обработчик (1 шт.)
**Задача:** превращать глыбу в строительный кирпич. **Базовая обработка:** 3.0 с. Состояния: `WaitingInput → ReserveOutput → TakeRaw → Processing → DepositBrick → WaitingInput`.

Работает в стационарной мастерской, никуда далеко не ходит. Может простаивать без сырья или из-за полного склада кирпичей. Новый цикл начинается только при свободном месте под результат.

## 4.4. Строитель (1 шт.)
**Задача:** укладывать кирпичи в строго заданном порядке. **Базовое время укладки:** 2.4 с за кирпич. **Скорость ходьбы:** 3.2 ед./с.

Состояния: `WaitingBrick → TakeFromPlatform → WalkToTarget → Place → ReturnToPlatform → WaitingBrick`; по окончании ряда: `AdvanceRow`.

- Сначала заполняет левую нижнюю клетку; каждый следующий кирпич — справа от предыдущего в текущем ряду.
- Один строитель, один кирпич в руках. Позиция цели рассчитывается по формуле геометрии.
- При новом ряду строитель поднимается по лесам; «прыжков» и телепортации нет.
- Ускорение строителя влияет **и на ходьбу, и на укладку**, чтобы улучшение оставалось полезным при длинных рядах.

## 4.5. Общие правила агента
У каждого рабочего есть `workerId`, `role`, `state`, `stateRemainingTime`, `pathSegment`, `position`, `reservedResourceIds` (для носильщика), `cargoIds`. Логическая позиция и инвентарь сохраняются. Каждый агент имеет не более одной активной задачи; переходы между состояниями должны быть детерминированными при фиксированном шаге симуляции.

# 5. Экономика и улучшения

## 5.1. Валюта
Одна валюта — **монеты казны**. Начальный баланс: **120**. Каждая установка кирпича даёт **+10** монет. Завершение каждого из 30 рядов приносит **+50** дополнительных монет. Суммарный заработок за полностью построенную пирамиду: `900*10 + 30*50 = 10 500` монет, без учёта стартового баланса.

Нет расходов на «зарплату», энергии, расходников и случайного дохода. Производство никогда не останавливается из-за нулевого баланса. Неиспользованные монеты сохраняются на финальном экране.

## 5.2. Каталог улучшений
| Код | Улучшение | База | Эффект | Предел |
|---|---|---:|---|---:|
| `MINER_SPEED` | Инструмент каменотёса | 40 | скорость добычи и ходьбы ×1.18 за уровень | 8 |
| `DRESSER_SPEED` | Инструмент кирпичника | 35 | скорость обработки ×1.18 за уровень | 8 |
| `BUILDER_SPEED` | Навык строителя | 45 | скорость ходьбы и укладки ×1.18 за уровень | 8 |
| `PORTER_SPEED` | Снаряжение носильщиков | 60 | скорость движения и погрузки/разгрузки ×1.15 | 8 |
| `PORTER_CAPACITY` | Волокуши | 200 / 650 / 1800 | вместимость **всех** носильщиков: 1→2→3→4 | 4 |
| `HIRE_PORTER` | Нанять носильщика | 100 | +1 носильщик; старт 1 | 8 носильщиков |

- Все скоростные улучшения начинаются с **уровня 1**. При переходе с уровня `L` на `L+1` стоимость: `roundTo5(baseCost * 1.50^(L-1))`. Выход за пределы уровня запрещён.
- Цена найма при текущем количестве носильщиков `N`: `roundTo5(100*1.70^(N-1))`, где стартовое `N=1`; покупка при `N=8` недоступна.
- `roundTo5(x)` — математическое округление до ближайшего кратного 5, ровно половина вверх.
- Все улучшения применяются сразу; длительность уже начатого действия пересчитывается **по оставшейся доле работы**, чтобы не терять или не получать бесплатное время.
- Покупка атомарна: проверить баланс и лимит → списать монеты → увеличить уровень/число ботов → сохранить → обновить UI.
- Нет отката улучшений. Цены конфигурируются, но не вычисляются внутри представления.

## 5.3. Узкие места
Для интерфейса показывается оценочная эффективность каждой станции за последние 30 с: глыб/мин, кирпичей/мин и кирпичей на стройке/мин. Это **диагностика**, а не скрытое влияние на производство.

Подсказка «узкое место» определяется по блокировкам за 30 с: если этап простаивал из-за недостатка входа или переполнения выхода, UI сообщает причину. Например: «Носильщики не успевают: склад сырья пустует» или «Строитель не успевает: площадка заполнена».

# 6. Тайминг, idle и баланс

## 6.1. Симуляционное время
- Логика выполняется с фиксированным шагом `dt=0.1` с. Время в секундах игрового мира равно реальному времени в активной игре (1:1).
- Все длительности и скорости берутся из конфигурации; рендер плавно интерполирует положение между двумя логическими состояниями.
- Пауза останавливает симуляцию и не засчитывается как офлайн-время, если игрок остаётся на экране паузы.
- При сворачивании игра сохраняется, а время отсутствия считается при следующем возвращении.

## 6.2. Офлайн-прогресс
- Лимит — **4 часа** за один период отсутствия; сверх лимита производство не симулируется.
- Используется **та же** логическая модель, только без анимации и визуальных объектов. Шаг может оставаться 0.1 с, ускоренный прогон разбивается на короткие порции между кадрами загрузки UI.
- Во время отсутствия боты продолжают работу, но **сами не покупают улучшения**. Наличные доходы, лимиты складов, зарезервированные глыбы, 100 глыб на слой и очередь строительства сохраняются.
- Время отсутствия: `clamp(nowUtc - lastSavedUtc, 0, 4 h)`. При отрицательном значении (часы устройства переведены назад) принимается 0. В этой одиночной офлайн-игре защита от ручной подмены времени не является целью MVP.
- По возвращении экран сводки показывает: отсутствие, добыто, доставлено, обработано, установлено, монет получено, открытые слои/ряды. Если пирамида завершена, выводится финал.
- Баланс тестируется **и с офлайн-прогоном, и без него**, чтобы уровни не пропускались и деньги не начислялись повторно.

## 6.3. Балансовые ориентиры и метод проверки
- При старте покупка второго носильщика должна заметно уменьшать задержку на ранней/средней стадии.
- Примерно на третьем–четвёртом слое карьера транспорт должен стать значимым ограничением без улучшений.
- Покупка скорости каменотёса бесполезна, если в карьере постоянно заполнена очередь из 15 глыб: это осознанный учебный пример узкого места.
- К завершению прокачки путь транспорта увеличивается, но игрок способен компенсировать рост наймом/вместимостью/скоростью.
- **Целевое время 60–120 минут — гипотеза**, а не гарантия. Нужен автоматический прогон 900 ресурсов для сценариев «без покупок», «дешёвые оптимальные покупки», «хаотичные покупки»; при необходимости корректируются времена, множители и цены в конфиге.

# 7. Интерфейс и управление

## 7.1. Основной экран (альбомный)
- **Верхняя панель:** монеты, прогресс `X/900`, текущий ряд `R/30`, текущий слой карьера `S/9`, кнопка паузы/настроек.
- **Центр:** игровая сцена; слева карьер и рампа, по центру запасы/обработчик, справа пирамида. Камера по умолчанию показывает максимально большую часть цепочки.
- **Нижняя панель:** кнопки «Добыча», «Носильщики», «Обработка», «Строительство». По нажатию открывается карточка с текущим уровнем, эффектом, стоимостью следующего улучшения, кнопкой покупки и причиной простоя.
- **Отдельная строка:** условные индикаторы заполнения карьера, сырьевого склада, склада кирпичей и строительной площадки; нажатие даёт числовые значения.
- **События:** короткие ненавязчивые уведомления «Новый слой карьера», «Ряд завершён: +50».

## 7.2. Камера
- Одним пальцем: горизонтальное перетаскивание сцены; двумя: масштабирование в пределах `0.8–2.0` от базового масштаба, камера ограничена миром.
- Кнопка «Вся стройка» восстанавливает базовую точку обзора. Нажатие на бота подсвечивает роль и открывает соответствующее улучшение.
- Игровой интерфейс не двигается вместе с камерой. Изменение масштаба не влияет на игровые координаты или логику.

## 7.3. Обучение (до 60 секунд)
1. Подсветить добычу первой глыбы: «Каменотёс добывает сырьё».
2. Подсветить носильщика на обратном пути: «Доставка ограничивает скорость стройки».
3. Показать кирпичника и строительный подъёмник.
4. После первых +10 монет открыть панель улучшений; указать, что деньги зарабатываются установкой кирпичей.
5. После первой установки предложить купить второго носильщика за 100 монет (начальный баланс позволяет покупку), **но не требовать** её для дальнейшей игры.
6. Сохранить признак `tutorialCompleted`; подсказки можно отключить.

## 7.4. Финал и управление сеансом
После установки последнего кирпича открывается экран «Пирамида возведена»: длительность текущего прохождения, общее число установленных кирпичей (900), монеты в остатке, уровни улучшений, кнопки «Осмотреть пирамиду» и «Новая игра». Кнопка «Новая игра» требует подтверждения, поскольку перезаписывает текущий прогресс. После финала все производственные действия и покупки отключены. Кнопка Android «Назад» закрывает открытое окно; на главном экране вызывает меню паузы, а не немедленно выходит из приложения.

## 7.5. UX и доступность
Читаемый шрифт на небольших устройствах, крупные зоны касания (не менее примерно 44–48 dp), возможность отключить тряску камеры, звуки и музыку отдельно, текстовые подписи к цветовым индикаторам. Всплывающие сообщения не перекрывают кнопки покупки.

# 8. Визуал и звук

## 8.1. Арт-направление
Мультяшная 2D боковая перспектива, тёплая песчаная палитра, выразительные силуэты работников. Пирамида сначала видна как прозрачный контур будущего сооружения, затем заполняется **поштучно**. Карьер показывается в разрезе, открытые клетки остаются пустыми. Леса и рампа расширяются автоматически на переходах.

## 8.2. Производственные анимации
- Каменотёс: подход → 2–3 удара киркой → глыба отделяется → клетка карьера исчезает.
- Носильщик: подход → крепление верёвки → волочение 1–4 глыб на волокуше → разгрузка.
- Кирпичник: обтёсывание глыбы → появляется кирпич на выходе.
- Подъёмник: кирпич поднимается по канату к активному ряду.
- Строитель: берёт кирпич → идёт → устанавливает → короткая пыль → возврат.
- Новая высота и новый слой сопровождаются небольшим визуальным акцентом, без остановки симуляции.

## 8.3. Аудио
Пять коротких SFX: удар камня, волочение/скрип, обработка, установка кирпича, покупка улучшения. Одна спокойная зацикленная фоновая композиция, отдельные громкости музыки/SFX, по умолчанию без постоянного громкого звука от каждого из сотен повторений: применяется кулдаун и приоритет звуков.

# 9. Техническая архитектура

## 9.1. Принцип разделения
**Симуляция является единственным источником истины.** Она реализована на GDScript 2.0 в классах `RefCounted`, не наследующих `Node` и не обращающихся к сцене, физике или UI. Узлы Godot только отображают состояние и передают команды покупки/камеры. Модель допускает запуск из headless-режима Godot без создания игровой сцены.

Слои:
1. `Config`: сериализуемые значения, граф маршрутов, параметры ботов, экономики и геометрии.
2. `Domain`: `GameState`, `ResourceState`, `WorkerState`, инварианты, доменные события.
3. `Simulation`: карьер, распределение задач, движение, производство, строительство, деньги, апгрейды.
4. `Application`: игровой цикл, команды UI, загрузка/сохранение, офлайн-прогон.
5. `Presentation`: `TileMapLayer`, `Sprite2D`, `AnimatedSprite2D`, пулы визуальных глыб/волокуш, `CanvasLayer`/`Control` для HUD, `AudioStreamPlayer`, `Camera2D`.

Никаких вызовов из Domain к Presentation. События можно собирать в очередь `GameEvent` для отображения, но после офлайн-прогона UI получает агрегированную сводку, а не 900 эффектов.

## 9.3. Структура данных
`GameState` включает: `schemaVersion`, `saveUtc`, `elapsedSimSeconds`, `currency`, `minedCount`, `placedCount`, `quarryReady[]`, `rawStorage`, `finishedStorage`, `platformStorage`, `processorWorkItem`, `liftWorkItem`, `builderCarryItem`, `workers[]`, `upgradeLevels`, `currentRow`, `tutorialCompleted`, `gameCompleted` и необработанные события начислений (если используются).

`StoneRecord`: `id`, `sourceLayer`, `sourceIndex`, `status`, `reservedByWorkerId` (или null). Установленные блоки **не требуют 900 записей**: их позиции однозначно восстанавливаются из непрерывного `placedCount`; для ресурса при установке ID можно удалять из активных записей, сохраняя счётчики.

`WorkerState`: `id`, `role`, `fsmState`, `x`, `y`, `moveFrom`, `moveTo`, `segmentProgress`, `actionRemaining`, `cargoIds`, `reservedIds`, `speedLevelAtActionStart` (если нужен для пересчёта). При реконструкции активных задач после загрузки проверяются все связи.

## 9.4. Порядок обновления в тике
1. Принять и атомарно применить команды игрока (покупки, пауза).
2. Завершить текущие таймеры/перемещения агентов, срок которых истёк.
3. Перенести ресурсы между узлами **атомарно**, обновить резервации и начисления.
4. Обновить состояние карьера/нового слоя/нового ряда, если сработали условия.
5. Выдать новые задачи в фиксированном порядке (производство → подъёмник → строитель → транспорт → добыча); порядок документирован и не зависит от очередности вызовов `_process()` или `_physics_process()` в Godot.
6. Обновить счётчики для UI и добавить доменные события.

Если несколько действий завершаются в один тик, порядок по `workerId`, затем по типу операции. Отрицательных таймеров и многократной обработки одной операции быть не должно. Наиболее строгий вариант реализации — обработчик событий внутри каждого тика, пока все завершения не обработаны, с ограничением от бесконечного цикла.

## 9.5. Оптимизация
- Не использовать `RigidBody2D`/`CollisionShape2D` для кирпичей и маршрутов; только математические координаты и логические сегменты.
- Построенную пирамиду отображать через **`TileMapLayer`** (отдельный слой) или сгруппированную статическую сетку. Укладка меняет одну клетку, а не создаёт бесконечные объекты.
- Карьер отображать вторым `TileMapLayer`; удаление камня меняет одну клетку. Для визуально сложной земли допускаются чанки, но не требуются на MVP.
- Движущиеся волокуши, глыбы и пыль берутся из пулов. Не создавать/удалять объекты в цикле каждый раз.
- 1 `SimulationRunner` на `_physics_process(delta)` с аккумулятором шага 0,1 с вместо индивидуальной игровой логики в `_process()` каждого работника; видимые агенты только интерполируются в `_process(delta)`. При лаге ограничить число шагов в кадре, не теряя накопленное симуляционное время.
- Конфигурации (`Resource` или JSON) загружать один раз; в горячих циклах избегать частого создания `Dictionary`, `Array`, строк и временных узлов.
- Пересчитывать экранные числа по изменению состояния, а не каждую отрисовку. Аудио и пыль не запускать на офлайн-тиках.
- Фокус оптимизации: отсутствие лагов при 8 носильщиках и почти готовой пирамиде; ECS и сторонние библиотеки для MVP не требуются.

## 9.6. Особенности цикла Godot
- Онлайн: `SimulationRunner` получает `delta` из `_physics_process(delta)`, накапливает время и выполняет логические тики по 0,1 секунды. Графические узлы не решают, когда ресурс добыт или уложен.
- Офлайн: тот же `step_simulation(0.1)` вызывается в headless-цикле; для быстрого расчёта запрещены вызовы `await`, `Timer`, `Tween` и любые обращения к `SceneTree` из модели.
- Состояния и инвентарь сериализуются в JSON через явные `to_dict()/from_dict()`. Godot `Node`, `Resource`, `ObjectID` и `Vector2` не сохранять напрямую: координаты переводить в массив `[x, y]`, остальные значения в JSON-совместимые типы.
- Запись сохранения: создать каталог через `DirAccess.make_dir_recursive_absolute`, записать временный JSON в `user://`, закрыть файл, перечитать и проверить, затем сохранить прошлый файл как backup и заменить основной. Проверять коды ошибок `FileAccess`/`DirAccess`; на Android не полагаться на абсолютные системные пути.
- Для тестового запуска без окна: `godot --headless --path . --script res://tests/run_all.gd`; тестовый скрипт наследует `SceneTree` и завершает выполнение с ненулевым кодом при ошибках.

# 11. Сохранения, жизненный цикл, ошибки

## 11.1. Сохранение
Автосохранение раз в 30 с активной игры, после каждой покупки, завершения ряда, сворачивания/потери фокуса и выхода. Формат: JSON с `schemaVersion`, временем UTC и контрольной суммой. Запись: временный файл → проверка → атомарная замена основного; при ошибке доступна предыдущая резервная копия. На Android хранение в `user://` (например, `user://saves/save_v1.json`), через `FileAccess` и `DirAccess`.

Обязательное правило: сохраняются активные таймеры, перемещения, зарезервированные глыбы и занятые места назначения. Нельзя сохранять только деньги и номера рядов, иначе после загрузки появятся дубликаты или исчезнет груз.

## 11.2. Миграции
Если `schemaVersion` старее текущей, последовательно применить функции миграции. Неподдерживаемое будущее сохранение не затирать автоматически. При невозможности загрузки показать понятное сообщение и предложить восстановить резервную копию или начать новую игру.

## 11.3. Проверка инварианта ресурсов
В любой момент:

**`900 = ещё не добытые + готовые в карьере + в руках/волокушах носильщиков + на складе сырья + в обработке + на складе кирпичей + в подъёмнике + на площадке + у строителя + уложенные`**.

Резервация **не** прибавляет ещё одну глыбу: это метаданные существующего объекта. Проверка запускается в тестах после каждого перехода, в dev-сборке по необходимости. Изменение валюты только через `EconomySystem`; монеты не могут уходить в минус.

# 12. События и крайние случаи

| Ситуация | Требуемое поведение |
|---|---|
| Карьер заполнен 15 глыбами | каменотёс ждёт, носильщики продолжают рейсы |
| Склад сырья полон | новые рейсы не начинаются; уже зарезервированные места сохраняются |
| Склад кирпичей полон | обработчик не начинает новую глыбу, пока не освободится место |
| Площадка полна | подъёмник ждёт, строитель продолжает класть |
| Не хватает денег | кнопка улучшения неактивна, производство идёт |
| 100-я глыба добыта | каменотёс возвращается, рампа достраивается, старые глыбы остаются |
| Закончился ряд | +50 монет ровно один раз, открыть следующий ряд |
| Добыто 900 глыб | каменотёс останавливается; остальные заканчивают работу |
| Уложено 900 кирпичей | остановить производство, начислить финальный бонус ряда, показать победу |
| Сохранение в середине рейса | восстановить груз, положение, резерв и остаток времени без потерь |
| Игрок свернул на 5 часов | зачесть максимум 4 часа, показать отчёт |
| Изменено системное время назад | офлайн-прогресс 0 секунд, предупреждение только при необходимости |
| Недоступен файл сохранения | попытаться загрузить backup; не перезаписывать неисправное состояние |
| Куплен апгрейд посреди действия | пересчитать оставшуюся долю работы, исключить двойное завершение |

# 13. Телеметрия для разработки
В релизном MVP не требуется серверная аналитика. Локально для отладки логируются: `purchase`, `layer_completed`, `row_completed`, `inventory_blocked`, `offline_applied`, `save_failed`, `pyramid_completed`. В debug-оверлее: FPS, длительность симуляционного тика, активные агенты, резервации, очередь камней, скорость каждого этапа, суммарное время игры. Логи без персональных данных.

# 14. Приёмочные критерии и тестирование

## 14.1. Функциональные критерии
1. Пирамида содержит ровно 30 рядов и 900 клеток; геометрия центрирована.
2. Карьер содержит ровно 9 слоёв по 100 глыб; каждая следующая точка дальше от пирамиды.
3. После 100 глыб каменотёс идёт назад и спускается, лестница удлиняется.
4. Ресурсный инвариант на всех шагах равен 900, включая сохранение/загрузку.
5. Две волокуши не резервируют одну и ту же глыбу; склад не переполняется.
6. Пустые/заполненные буферы корректно останавливают нужную стадию.
7. Покупки проверяют цены, пределы и деньги; события не дублируются.
8. Доход за завершение: 9000 от кирпичей и 1500 от рядов.
9. Постройка завершается лишь после установки 900-го кирпича.
10. Сохранение во всех состояниях агента не приводит к пропаже или удвоению ресурса.
11. Результат одной симуляции, разбитой сохранением/загрузкой, совпадает с непрерывной при одинаковых действиях и шаге времени.
12. Офлайн-прогон 4 часа не перескакивает лимиты складов и останавливается после завершения пирамиды.
13. Игра не требует нажатий для продолжения производственной цепи.
14. При 8 носильщиках не возникает мёртвых блокировок и зависших резервов.
15. На поддерживаемом устройстве целевые 30 FPS стабильны на финальной стадии, 60 FPS желательны; проверяется профилировщиком.
16. Новая игра полностью сбрасывает состояние, а настройки громкости сохраняются отдельно.

## 14.2. Автотесты
- Unit: `B(r)` и сумма 900, индексы карьера, округление цен, цена найма, инвариант запасов, лимиты, расчёт маршрутов и пересчёт времени после улучшения.
- Simulation: 900 глыб без UI, массовые покупки, несколько одновременных разгрузок, заполнение складов, переходы уровней и рядов.
- Save/load: сериализация в каждом значимом состоянии FSM, проверка обратной совместимости схемы.
- Offline: сверка непрерывной 4-часовой симуляции с ускоренным прогоном при одинаковом `dt` и без покупок.
- UI smoke: купленная кнопка меняет уровень и цену, новые ряды появляются, камера не разрушает координаты.

# 15. Поэтапный план производства

## Этап A. Чистая модель мира
**Результат:** модель `GameState`, конфиг, формулы 900/900, тесты геометрии и инвариантов. Графики и анимации не нужны.

## Этап B. Конвейер в headless-режиме
**Результат:** все 4 роли, буферы, задачи, движение по логическим маршрутам, 900 кирпичей и победа без создания `Main.tscn`. Автотесты блокировок.

## Этап C. Баланс-песочница
**Результат:** CSV-прогоны с разными стратегиями улучшений; скорректированные цифры, проверка времени партии.

## Этап D. Отображение сцены
**Результат:** `TileMapLayer` карьера и пирамиды, рабочие/волокуши из пулов, `Camera2D`, базовые переходы и леса.

## Этап E. Игрок и UI
**Результат:** экран денег, прогресса, простоя, карточки улучшений, найм, подсказки и обучение.

## Этап F. Сохранения и офлайн
**Результат:** снапшоты в любой момент, миграция версии, 4-часовой прогон, отчёт и восстановление после ошибок.

## Этап G. Полировка и оптимизация
**Результат:** финальные спрайты, SFX, анимации, профилирование Android, минимум 30 FPS, QA всех крайних случаев.

**Definition of Done для MVP:** игрок может запустить новую игру, не нажимая на работников увидеть весь производственный цикл, покупать улучшения, закрыть приложение и получить правильный офлайн-прогресс, а затем построить последнюю из 900 плит без ошибок экономики и логики.

# 16. Риски и решения

| Риск | Вероятное проявление | Решение |
|---|---|---|
| Слишком длинная партия | игрок ждёт, не может влиять | headless-баланс до производства арта; ускорить ранние циклы |
| Число ботов перегружает кадр | просадки FPS | единый тик, пулы, `TileMapLayer`, минимум обновлений UI |
| Плохая читаемость на телефоне | мелкие рабочие на общей панораме | zoom, фокус на сегмент, крупный UI |
| Логистика кажется бессмысленной | все апгрейды дают равную пользу | статистика простоя, разные цены, рост расстояния |
| Баг дублирования предметов | больше 900 уложенных / отрицательные запасы | атомарные переходы, резервации и инвариант |
| Застревание работников | ожидание места, которое занято навсегда | бронирование входного места до начала рейса, watchdog в dev-режиме |
| Офлайн отличается от онлайна | пропущенные бонусы, отрицательные остатки | одна модель и одинаковый dt; автосравнение |
| Автоматический подъёмник выглядит «магией» | кирпич мгновенно попадает наверх | видимый канат, заданное время подъёма, буфер 6 |

# 17. Журнал ключевых проектных решений

1. **Каменщик переименован в каменотёса**, чтобы не путать добычу камня с укладкой кирпичей. Роли: каменотёс, носильщик, кирпичник, строитель.
2. Добыча ведётся **глыбами**, а не готовыми кирпичами; переход раз в **100 добытых глыб**.
3. Пирамида из 30 нечётных рядов даёт ровно 900 кирпичей; карьер из 9×100 даёт ровно 900 глыб. Ресурсы сбалансированы без остатка.
4. Глыбы на волокушах тянут за верёвку по лестнице-рампе, не несут вертикально без опоры.
5. Карьер и пирамида меняются по независимым правилам; их объединяет конвейер ресурсов.
6. У строителя есть видимый механический подъёмник и запас кирпичей на текущем ряду, поэтому кирпичи не телепортируются наверх.
7. Один каменотёс, один кирпичник, один строитель; масштабируется только число носильщиков и эффективность работников.
8. Микроменеджмента ручных приказов нет; игрок управляет производительностью.
9. В MVP только одна пирамида, без престижа и бесконечного цикла: финальная цель определена заранее.
10. Подробные значения баланса являются **стартовыми константами**, окончательно утверждаются лишь после симуляций.
