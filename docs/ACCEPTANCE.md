# Приёмка Windows-обоев

## Как найти Godot

Для проверок используйте консольную сборку Godot 4.7.2 stable для Windows x64. Пустой вывод `Get-Command godot` означает, что команда недоступна по этому имени. Распакованный редактор обычно запускается по полному пути.

На рабочем ПК «Пирамиды» проверен следующий путь. Выполните в PowerShell.

```powershell
$piramidaGodot = Join-Path $env:TEMP 'piramida-godot-task05/Godot_v4.7.2-stable_win64_console.exe'
if (Test-Path -LiteralPath $piramidaGodot -PathType Leaf) {
    & $piramidaGodot --version
}
```

Временная папка может быть очищена. Если файла там нет, проверьте расположения в таком порядке.

1. Выполните `Get-Command godot,godot_console,Godot_v4.7.2-stable_win64_console.exe -CommandType Application -ErrorAction SilentlyContinue`. Если найден редактор, возьмите полный путь к консольному EXE из свойства `Source` или проверьте соседний файл с суффиксом `_console.exe`.
2. Выполните `Get-Process *Godot* -ErrorAction SilentlyContinue | Select-Object -ExpandProperty Path`. Если открыт редактор, ищите консольный EXE в той же папке.
3. Поищите `Godot_v4.7.2-stable_win64_console.exe` в папке проекта, в `%TEMP%`, в `Downloads` и в каталоге, куда распакован Godot. Для поиска в конкретной папке используйте `Get-ChildItem -LiteralPath $env:TEMP -Recurse -File -Filter 'Godot_v4.7.2-stable_win64_console.exe' -ErrorAction SilentlyContinue`, подставив нужный каталог.

Присвойте найденный полный путь переменной `$piramidaGodot`. Команда `& $piramidaGodot --version` должна завершиться с кодом 0 и вывести `4.7.2.stable` с идентификатором сборки. Если редактор не найден, для прогона понадобится распаковать стандартную сборку Godot 4.7.2 stable Windows x64. Если прогон заблокирован, укажите проверенные каталоги или ошибку вызова `--version`.

Сценовый тест и флаг `--verify-wallpaper-cycles` в свежем экспорте начинают стройку с нуля и создают отдельный временный каталог на запуск. В нём хранятся снимки, резервы и файлы проверок миграции. Godot удаляет каталог при штатном завершении. Штатный запуск читает и записывает `user://wallpaper/save.json`.

Используйте отдельный `APPDATA` для воспроизводимых прогонов и проверки старых EXE, диагностика которых пишет в штатный слот. Чтобы проверить изоляцию, поместите валидные контрольные `save.json` и `save.json.bak` в слот обоев в выделенном `APPDATA` и сравните их SHA-256 до и после запуска. Запустите тест сцены из корня проекта в том же сеансе PowerShell, где задан `$piramidaGodot`.

```powershell
$piramidaAppData = $env:APPDATA
try {
    $env:APPDATA = Join-Path ([IO.Path]::GetTempPath()) ("piramida-check-" + [guid]::NewGuid())
    New-Item -ItemType Directory -Force -Path $env:APPDATA | Out-Null
    $piramidaLog = Join-Path $env:APPDATA 'wallpaper-cycles.log'
    & $piramidaGodot --headless --path . --log-file $piramidaLog --script res://tests/wallpaper_cycles.gd
    if ($LASTEXITCODE -ne 0) {
        throw "Тест сцены завершился с кодом $LASTEXITCODE. Журнал: $piramidaLog"
    }
} finally {
    $env:APPDATA = $piramidaAppData
}
```

Команда явно загружает тест Windows-обоев. Основная сцена проекта — `res://scenes/wallpaper.tscn`; её можно запускать через F5. Для проверки EXE используйте тот же блок с выделенным `APPDATA`, запустите `Start-Process -FilePath $piramidaExe -ArgumentList @('--headless', '--log-file', ('"{0}"' -f $piramidaLog), '--', '--verify-wallpaper-cycles') -WindowStyle Hidden -PassThru -Wait` и проверьте свойство `ExitCode` и журнал. Переменная `$piramidaExe` должна содержать полный путь к проверяемой сборке. Для длительности кадров, GPU, памяти и привязки к Explorer нужны отдельные проверки рабочего стола.
