# Единый план обновления «Пирамиды»

> Историческая редакция плана. Текущая реализация описана в [ГДД](GDD.md#wall-01-живые-обои-windows-x64), открытые проверки — в [приёмке](ACCEPTANCE.md#живые-обои-windows-x64). Для дальнейшего рефакторинга есть [план оптимизации](OPTIMIZATION.md).

Финальная редакция плана от 14 ноября 2026. Статус: **только планирование**. Этот документ полностью заменяет прежнюю последовательность дополнений. Код, сборки и новые спрайты в рамках рефакторинга плана не изменяются. План снижает риски проверяемыми этапами, но не обещает отсутствие ошибок без реализации и тестирования.

## 1. Целевой результат и область работ

Обои показывают компактную, читаемую стройку: узкий глубокий карьер, блоки размером с кирпич пирамиды, бесшовный песок, согласованные объекты и четыре состояния суток по местным часам компьютера. Люди используют 2–3 кадра по действию, поворачиваются по движению, тянут волокушу только с грузом. Кирпич поднимается, едет по верхнему горизонтальному тросу к началу текущего ряда, затем строитель тянет его к месту укладки.

Целевой продукт — самостоятельные обои Windows x64 без Lively. Разделение области изменений:

- **Первый выпуск — обои Windows.** Компактная геометрия, полировка окружения и время суток сначала подключаются здесь. Нет сохранений партии, экономических действий и звука; остаются автоматическая стройка и 5 секунд показа результата.
- **Обычная игра и Android — только сохранение работоспособности.** Новые функции предназначены для обоев. Перенос функций и миграция сохранений игры не входят в этот план; общие изменения проходят регрессии на прежнем профиле.

Выпуск обоев не означает, что новая геометрия уже перенесена в игру. Старую конфигурацию игры нельзя молча заменить параметрами обоев. Новые анимации не входят в задачу статической полировки, но остаются обязательной отдельной задачей этого общего плана.

## 3. Решения и параметры, требующие проверки

### Карьер

Прежнее предложение расширить карьер до 36 единиц отменено. Базовый кандидат: **30 слоёв × 30 клеток = 900**, клетка **0,36 × 0,28** (36×28 px при 100 px/ед.). Ширина 10,8 вместо 18; полная глубина 8,4 вместо 7,2; нижняя рабочая отметка −8,12. Размеры клеток брать из единого источника размеров кирпича для нового профиля мира.

Это ещё не утверждённая компоновка: рампа при 30 слоях может занять существенную ширину справа. Кандидат длины сегмента при прежнем уклоне — 0,42; проверить горизонтальный вынос и пересечения с мастерской. Не сохранять прежние 1,2 автоматически. Конкретные параметры зафиксировать после макета. Слой карьера и ряд пирамиды — разные индексы, даже если их количество совпадёт.

### Доставка

«Актуальный слой пирамиды» означает current_row. Горизонтальный трос простирается от мачты до правой границы основания пирамиды, сейчас X=30,24. Каретка останавливается у начала текущего ряда, а не у следующего места укладки. Запас площадки остаётся 6, строитель берёт один кирпич.

Высота троса: верх текущего ряда плюс clearance. Clearance и длину подвеса выбрать по габаритам людей и груза в макете. Различать координату груза и каретки: каретка находится на тросе, кирпич ниже. Маршрут груза: склад → основание → вертикальный подъём → горизонтальная доставка → опускание на площадку. Точная последовательность точек должна начинаться и заканчиваться на существующих точках владения, без телепортации при приёме груза.

Сохранить одно состояние lift_brick и очередь сегментов, если этого достаточно. Весь путь материал принадлежит Owner.LIFT; единственная передача площадке — в конце. Первоначально сохранить полное время lift_seconds(row), распределив по длине нового маршрута. Проверить визуальную скорость: новая длина при том же времени может выглядеть слишком быстрой. Любое изменение длительности — отдельное явное решение с замером темпа. Мгновенная готовность пустого механизма у склада остаётся действующим правилом; не изображать её как физически проверенный обратный рейс.

### Время суток

Четыре состояния: утро, день, вечер, ночь. По новому требованию фиксированное расписание отменено: смешивание определяется высотой Солнца и восходящей/заходящей частью его реального пути для выбранного наблюдателя. Астрономический расчёт использует реальный момент UTC, полученный из системных часов; местный часовой пояс нужен для ввода и отображения времени. Координаты наблюдателя задаются отдельно: часовой пояс не определяет местоположение. См. раздел 7 — обязательное уточнение T1/T5/T9.

## 4. Порядок задач и условия завершения

Каждая задача заканчивается работающим проверяемым результатом и записью в PROGRESS. Не начинать зависимый этап, пока не выполнено его условие готовности. Полноценные сборки делаются после интеграции; исключение — минимальный экспорт W0 для проверки рабочего стола.

### Автономное выполнение в Codex и субагенты

**Это регламент для будущей реализации, не команда начинать её при чтении плана.** Только явный запрос пользователя выполнить весь этот план разрешает автономный переход между этапами. Запрос выполнить отдельный этап разрешает только этот этап; после него остановиться. При запуске всего плана Codex выступает главным исполнителем и координатором: читает действующие правила проекта, берёт первый доступный этап из последовательности T0 → W0 → T1–T7 → W1 → T8 → T9 → W2, доводит его до указанного критерия готовности, фиксирует результат в PROGRESS и без дополнительного подтверждения переходит к следующему доступному этапу. Сам факт написанного кода или отчёта не равен готовности. Не запускать внешний оркестратор и не создавать инфраструктуру управления агентами ради этого плана.

**Субагентов привлекать по необходимости, обычно одного на конкретную проверку; при простых правках обходиться без них:**

- **Архитектурный/предметный анализ** — независимо проверить рискованное решение перед изменением модели или платформенного кода (особенно T1–T3, T5, W0–W1). Для T5 отдельно сверить астрономические допущения и эталон; для W0–W1 — ограничения Windows.
- **Независимое ревью/QA** — после реализации проверить критерии готовности, тесты, регрессии и границы изменений (особенно T2–T3, T5, T7–T9, W1–W2). На T4/T6/T7 при наличии возможности отдельно проверить визуальные кадры, опоры, груз и соответствие макету.

Ревьюеры и предметные аналитики по умолчанию работают только на чтение: не редактируют файлы, не запускают изменяющие состояние команды и не исправляют собственные замечания. Исправления вносит главный агент. Если субагенту поручена реализация, главный агент заранее задаёт точный список принадлежащих ему файлов и интерфейсы; изменения за этими границами согласуются с координатором.

Главный агент сохраняет ответственность за изменения и итоговую приёмку; не допускает одновременной правки одних файлов несколькими агентами. Субагенту давать узкую задачу и конкретный проверяемый результат, а не дублировать целый этап. Цикл: **реализация → доступные проверки → при необходимости субагент-ревьюер → исправления → повторная проверка → PROGRESS → следующий этап**. Существующие тесты и сцены важнее словесного заверения о работоспособности. Не заявлять визуальную, системную или аппаратную проверку успешно пройденной, если фактически выполнен только headless-прогон.

Помимо файлов главный агент координирует общие ресурсы: импорт Godot и кэш .godot, каталоги сборок и экспорта, запущенные экземпляры приложения, окна для визуальных проверок и состояние Explorer. Импорт, экспорт в один каталог, управление одним окном и проверки с перезапуском оболочки выполняются последовательно одним назначенным исполнителем. Параллельные проверки допускаются лишь при подтверждённой изоляции ресурсов; разные редактируемые файлы сами по себе её не обеспечивают.

Отчёт каждого субагента содержит: границы задания; проверенные файлы/версию состояния; выполненные команды и фактические результаты; замечания с местом, причиной, приоритетом и способом воспроизведения/проверки; непроведённые проверки и ограничения; список изменённых файлов, если редактирование было поручено. Главный агент сопоставляет отчёт с актуальными изменениями и результатами проверок. После исправлений повторяет затронутые проверки; отчёт по старому состоянию не подтверждает новое. Формулировка «готово» без доказательств не закрывает этап.

При отсутствии ассетов, невыбранном наблюдателе для астрономической части T1/T5 или необходимости реальной проверки Windows отмечать конкретный блокер, не подменять исходные требования догадкой и по возможности продолжать независимые этапы без нарушения зависимостей. Если доступной работы больше нет, остановиться с точным списком препятствий. Продолжать в пределах возможностей текущей сессии; при её прерывании возобновлять работу по PROGRESS с первой незавершённой доступной задачи, не выдавая это за автоматический перезапуск Codex.

### T0. Зафиксировать исходную работоспособность

**Можно без новых спрайтов.** Проверить локальные изменения, запуск двух сцен, tests/run_all.gd и tests/wallpaper_cycles.gd. Снять исходные кадры начала, середины и конца стройки; записать размеры окна, длительность цикла и известные предупреждения. Не принимать старые записи журнала за текущий успешный прогон.

Сверить обращения к 9/100/0,8/18×80 в коде и тестах: отличать действующие ограничения от проверок конкретной конфигурации. Сохранить тестовые снимки обычной игры с грузом, активными маршрутами и переходом ряда как фикстуры совместимости.

**Готовность:** воспроизводимая база и список реальных ограничений; существующие ошибки отделены от новых.

### T1. Утвердить пространственный макет и контракты ассетов

**Разделение готовности:** T1a — компоновка стройки, геометрия и контракты рабочих; T1b — наблюдатель, проекция и контракт неба. Неизвестные координаты блокируют завершение T1b и астрономическую интеграцию T5, но не T1a и задачи T2–T4/T6–T7 после её приёмки. Для макета оставлять явно обозначенную область неба, не выдавая тестовые координаты за выбор пользователя.

**После T0 и W0; можно без финальных спрайтов.** На существующей графике сделать макеты трёх стадий для 1920×1080 и 1008×567. Одновременно учесть карьер 30×30, рампу, мастерскую, полный размер пирамиды, верхний трос с опорами и область неба. Подобрать масштаб людей, положение горизонта и поля камеры. Сначала компоновка, потом окончательная детализация.

Масштаб человека определяется телом/головой, не общим bbox кирки и саней. Сидящий остаётся ниже стоящего. Увеличение старых тел на 20–35% — только диапазон для сравнения, не готовое решение. Не масштабировать корень вместе с грузами. Учесть точки рук, ног, каната и место для саней позади строителя на левом конце настила.

Определить формат метаданных ассетов: роль, действие, кадры, исходное направление, опора ног, контакт инструмента/рук, масштаб. Для фонов — горизонт и безопасная область; для небесных тел — прозрачность и самостоятельный слой. Финальные фоны не должны содержать дубли движущихся светил.

**Готовность:** конкретные параметры и макеты без пересечений, достаточно крупные люди, все крайние положения помещаются. Не оставлять выбор рампы до финального экспорта.

### T2. Ввести профиль геометрии обоев

**После T1a; без новых спрайтов.** Создавать эффективную конфигурацию обоев из глубокой копии базового конфига и небольшого набора переопределений мира. Не копировать весь баланс и не менять общие словари на месте. Передавать одну эффективную конфигурацию в Simulation.for_wallpaper и world.setup. Не использовать art_set как скрытый переключатель логики модели.

Проверить начало каждого слоя, доступ к последней клетке, пути пустого и гружёного носильщика, все 900 ID, отсутствие столкновения маршрута с мастерской. Замерить полный цикл и ожидания, не компенсировать их скоростями молча.

**Готовность:** обои строят 900 кирпичей с новой геометрией; обычная игра использует прежний профиль и проходит регрессии.

### T3. Реализовать верхнюю доставку на модели и временной графике

**После T2 и утверждённых габаритов T1a; не ждёт финальных небесных спрайтов.** Изменить world_geometry и construction_production, сохранив владение и атомарные передачи. Проверять успешность queue_move; новый маршрут обязан совпадать с концом предыдущей фазы. Временная линия троса/каретка используют ту же геометрию, что модель, а не собственные формулы.

При последнем кирпиче ряда остановить назначение новых рейсов, дождаться возвращения строителя и завершения активной доставки к старой площадке. Затем согласованно переместить площадку с запасом и трос за rebuild_platform; строитель проходит climb_to_platform, после чего выдача возобновляется. Не менять цель уже летящего кирпича. После 900-й укладки не запускать переход следующего ряда.

Проверки: ряды 0, 1, 15, 29; полный буфер; одновременное прибытие и последняя укладка; нулевые сегменты; ровно одна передача груза. Новую маршрутизацию включить для обоев через явный профиль геометрии; для игры оставить прежнюю; проверить изоляцию в T8.

**Готовность:** цикл завершается без зависших резервов; груз не пересекает настил/людей; строительство не зависит от видимости или кадра анимации.

### T5. Время суток и жизненный цикл неба

**Логику можно разрабатывать на явно тестовых координатах после T1a; интеграция требует T1b и T4. Финальная визуальная приёмка ждёт спрайты.** Добавить отдельный контроллер часов и SkyPresenter. Контроллер принадлежит корню обоев вне пересоздаваемого World. При сбросе мира сохраняется состояние неба; новый мир получает текущую палитру до первого отображения. Небо обновляется и во время пятисекундного показа завершённой пирамиды. Удалить старый фоновый слой обоев при подключении нового, чтобы избежать двойного неба; фон игры сохраняется.

Источник времени подменяемый для тестов. Периодически сверять системные часы, между сверками интерполировать движение; после сна/возврата пересчитывать фазу. Пропущенные часы не воспроизводить. Резкую коррекцию времени мягко согласовать с новым состоянием. Не менять системные часы в тестах.

Солнце и Луна — рассчитанные топоцентрические положения, Луна может быть видна днём и отсутствовать ночью. Звёзды — каталог реальных направлений с суточным вращением, а пять спрайтов задают оформление, не случайное расположение. Облака — независимые скорости/высоты и перенос за границей кадра. Не вычислять движение облаков как time×меняющаяся скорость: это даёт скачки при смене суток; использовать непрерывную периодическую фазу. Все движения независимы от счётчика игрового цикла.

Порядок: небо → звёзды/светила → облака → дальний горизонт → площадка. Горизонт закрывает заходящие тела, облака перекрывают звёзды. Положения проецируются из высоты/азимута через единый ориентированный обзор неба; при resize сохраняются пропорции спрайтов и связь с горизонтом. Не переносить невидимые тела в кадр ради композиции.

Менять палитру песка, стен, пирамиды и предметов согласованно. Нижний предел яркости людей сохраняет читаемость ночью. Свет не меняет темп производства. Дымка, изменяемые тени и ночные огни — только дополнительная полировка после обязательной приёмки и при подходящих ассетах.

**Готовность:** четыре фазы, все границы и полночь, запуск в произвольное время, сон/возврат, смена часового пояса, перевод часов, два сброса стройки — без вспышек, дублей и скачков неба. Финальный внешний вид не считается завершённым на заглушках.

### Астрономическая модель (T5)

Добавить небольшой изолированный модуль расчёта неба с входом «UTC, наблюдатель» и выходом «высоты, азимуты, фаза/освещённость Луны, параметры сумерек». - Луна: собственное положение с учётом параллакса, а не отражённый путь Солнца. Допускать дневную видимость. Фазу и долю освещения вычислять по взаимному расположению, различать рост и убывание. Пять обычных изображений использовать как референсы фаз и текстуру; затмение исключить из регулярной последовательности. Для непрерывной физически согласованной фазы предпочтителен терминатор поверх единого диска полнолуния. Не переключать пять картинок через равные интервалы: отсутствуют отдельные четверти и новолуние. Новолуние не изображать ярким диском. Если используется дискретный подбор, явно обозначить приближение и устранить скачки контура. Ориентацию освещённой стороны согласовать с направлением на Солнце и положением наблюдателя; избегать произвольного зеркалирования кратеров.
- Звёзды: небольшой лицензированный каталог ярких звёзд с небесными координатами и величинами; преобразование через звёздное время в высоту/азимут. Созвездия сохраняют взаимную конфигурацию. Пять типов спрайтов распределять по яркости и оформлению, а не считать их пятью видами физических звёзд. Не добавлять случайные крупные звёзды, меняющие узнаваемое небо. Видимость зависит от сумерек, Луны и облаков; мерцание слабое, без изменения координат.
- Облака: отдельная художественная модель ветра, не небесная механика. Без метеоданных нельзя называть облачность реальной погодой. Движение непрерывное, с корректным перекрытием светил.

Размер Солнца и Луны выводить из углового размера и выбранной проекции. При необходимости читаемости допустим отдельно записанный художественный множитель, применяемый согласованно; он не меняет рассчитанных координат и не выдаётся за физически точный масштаб. Звёзды отображаются условными точечными ядрами с лучами, а не дисками реального углового диаметра. Согласование с масштабом людей означает композиционную читаемость, не одинаковые единицы для далёких светил и стройки.

Четыре фона остаются четырьмя палитрами, смешиваемыми по солнечной высоте и направлению её изменения. Зафиксировать диапазоны сумерек; учесть полярный день/ночь и отсутствие отдельных фаз суток, не принуждать все четыре состояния возникать ежедневно. Фиолетовый ореол солнца и цветовые градиенты — стилизация. Яркость Луны/неба и освещение площадки должны быть согласованы, но люди остаются читаемы ночью.

Для производительности пересчитывать эфемериды с заданным интервалом и интерполировать направления; азимут 359°→0° и околозенитные положения обрабатывать без скачков (предпочтительно интерполяция направлений). Каталог и эфемериды локальные. При перезапуске стройки сохраняется тот же наблюдатель и момент неба.

### Проверки и границы точности (T5/T9)

Перед интеграцией выбрать независимый эталон и закрепить тестовые даты/координаты. Предлагаемая целевая точность положения Солнца/Луны — до 0,5° вне области нестабильной рефракции у горизонта; окончательный допуск подтвердить выбранным алгоритмом. Не смешивать геоцентрические эталоны с топоцентрическим расчётом, видимую высоту — с геометрической. Отдельно проверять восходы/заходы и описывать атмосферные допущения.

Тесты: оба полушария, экватор и высокая широта, солнцестояния/равноденствия, полярные случаи, новолуние/полнолуние/рост/убывание, дневная Луна, смена UTC-даты, долготы около ±180°, азимут через 0°, изменение часового пояса без изменения UTC. Сверить реальные направления звёзд и ориентацию освещённой Луны. Проверить весь цикл на подставном времени без изменения часов пользователя. Финальная приёмка T5 ждёт подготовки полученных лунных файлов, облаков, выбора наблюдателя и согласования ночного ландшафта.

Источники для алгоритмов и эталонных соглашений:

- USNO, преобразование координат в высоту и азимут: https://aa.usno.navy.mil/faq/alt_az
- USNO, определения восхода, захода и сумерек: https://aa.usno.navy.mil/faq/RST_defs
- USNO, справочные данные и API для проверки: https://aa.usno.navy.mil/data/api.html

Обновление критического пути: T1b включает выбор наблюдателя/проекции и согласование горизонта полученных фонов; T5 — проверяемую астрономическую модель вместо условного расписания; T9 — сравнение с эталоном. Остальные задачи и разделение игры/обоев сохраняются.

### Уточнение подготовки Луны и ночного фона

Лунные изображения получены и просмотрены в сообщении. Проверка файлового alpha ещё не выполнена: видимый тёмный квадрат и широкое свечение требуют проверки на светлом и цветном фоне. Если фон непрозрачен, отделить диск и ореол, не удаляя тёмные участки лунной поверхности по порогу яркости. Согласовать центр полного диска, его радиус и рисунок кратеров; не отражать текстуру для смены роста на убывание. Сначала проверить, что пять кадров представляют один и тот же диск, затем выбрать единое основание для маски освещения. Свечение вынести в отдельный слабый слой и уменьшать вместе с освещённой долей, чтобы новолуние не давало яркого ореола.

06_lunar_eclipse.png хранить как специальный ассет. Не включать его в обычный месячный цикл и не показывать затмение каждое полнолуние. Подключение возможно лишь по подтверждённому расчёту/таблице затмений с проверкой текущей фазы события и видимости Луны из выбранной точки. До такого расчёта ассет остаётся неактивным. Не выдавать красную полную Луну за корректную картину частичного затмения; промежуточное покрытие требует отдельной маски. Этот эффект не блокирует основную астрономическую систему.

Пользователь разрешил исправить ночной фон. На этапе подготовки T5 создать отдельную исправленную копию: взять геометрию горизонта и дюн из дневного/утреннего/вечернего набора, сохранить ночную сине-фиолетовую палитру и отсутствие встроенных небесных тел. Не менять форму земли при переходе в ночь. Привести фактический размер к общему формату 1920×1080, проверив исходные размеры, а не только имя файла. Оригинальный ночной фон сохранить. Проверить смешивание вечер→ночь и ночь→утро на весах 0/25/50/75/100% с игровым горизонтом: без двойных дюн, скачков линии земли, растянутых пикселей и чрезмерно яркой ночной полосы. Разрешение на эту правку зафиксировано; в текущем этапе планирования изображения ещё не редактируются.


## 8. Собственные обои Windows без Lively

Задача из другого чата разделена на W0/W1/W2: технический риск проверяется рано, надёжный жизненный цикл готовится до интеграционной приёмки, переносимый комплект выпускается последним. Это части основного плана, а не три альтернативных способа запуска. Порядок: **T0 → W0 → T1–T7 → W1 → T8 → T9 → W2**. W1 можно разрабатывать после W0 независимо от готовности графики, но завершить до T8/T9. T6 зависит от ассетов, а не от окончания T5.

### W0. Проверить самостоятельное размещение на рабочем столе

**После T0, до T1.** Использовать существующую сцену обоев и минимальный Windows x64 экспорт. Выбрать и проверить способ размещения её окна под значками и приложениями. Не считать обычное borderless-окно, always-on-bottom или снятие рамки выполнением задачи.

Исследовать WorkerW/Progman как кандидат интеграции с оболочкой Explorer. Это не гарантированный публичный контракт Windows для живых обоев: не обещать совместимость со всеми сборками. Не фиксировать HWND, имя окна или порядок детей оболочки навсегда. Изолировать поиск поверхности, привязку окна и восстановление в небольшом Windows-адаптере. Если нужен нативный host/helper или GDExtension, включить исходники, воспроизводимую команду сборки, лицензию и зависимости. Сравнить эти варианты по сложности и стабильности на текущем Godot, выбрать один; не реализовывать сразу несколько платформенных слоёв.

Проверить DPI-awareness родителя и окна Godot, стили окна и координаты после привязки. SetParent сам по себе не решает все вопросы DPI и оконных стилей. Не внедрять код в Explorer, не подменять оболочку и не использовать постоянный цикл принудительного перемещения поверх других окон. Обычный запуск без администратора.

В прототипе проверить экспортированный рендер под значками, двойной щелчок, контекстное меню и выделение значков, Win+D, переключение приложений и потерю поверхности Explorer. Окно не получает фокус, не перехватывает ввод, не появляется как игровое окно в панели задач/Alt+Tab. При невозможности привязки скрывать/останавливать рендер и показывать диагностируемое состояние через управление; не оставлять полноэкранное окно поверх рабочего стола.

**Готовность:** реально проверенный способ и зафиксированные в DECISIONS поддержанные версии Windows, ограничения, DPI-режим и архитектура помощника. Если способ не работает на целевой системе, решить этот риск до дальнейшей зависимости от его поведения. Не выдавать сам факт экспорта за проверку рабочего стола.

### W1. Управление, восстановление и нагрузка

**После W0; завершить до T8/T9.** Отделить Windows-host от сцены и модели. Host управляет окнами, мониторами, состоянием оболочки и политикой нагрузки; Godot — рендером и стройкой. Ввести небольшой явный контракт команд: готовность, прикрепление/переприкрепление, размер/монитор, pause/resume, завершение. При нескольких процессах — ограниченный текущим пользователем IPC с проверкой команд, ожиданием готовности и тайм-аутами, без произвольного выполнения команд.

Минимальное управление через значок в системном трее/отдельное окно настроек: запуск/пауза, выбор монитора, включение/выключение автозапуска, выход и диагностика. Это управление приложением, не игровой HUD поверх обоев. Настройки наблюдателя для астрономии разместить здесь; не требовать меню внутри стройки.

Один host на пользовательский сеанс; повторный запуск обращается к существующему экземпляру. Он отслеживает только собственные дочерние процессы и завершает их при выходе. Использовать надёжное владение процессами, например Job Object при выбранной многопроцессной схеме; не завершать процессы по общему имени Godot. При аварии рендера ограниченные попытки перезапуска с задержкой, без бесконечного быстрого цикла. При явном выходе не перезапускать.

Автозапуск — опция текущего пользователя без повышения прав, включаемая и отключаемая в настройках. Запуск после входа ожидает готовности оболочки. Ссылка указывает на устойчивый путь комплекта; перенос/удаление приложения требует обновления/удаления записи. Не создавать несколько механизмов автозапуска одновременно. Выход из приложения не отключает выбранный автозапуск следующего входа; отключение — отдельная команда.

Восстановление Explorer: обнаружить потерю родителя, скрыть и приостановить рендер; с ограниченной частотой найти новую поверхность и перепривязать окно. Восстановить и значок трея. Не хранить старый HWND после перезапуска оболочки. TaskbarCreated полезен для уведомления о создании панели задач, но не является единственным доказательством готовности поверхности обоев. Если восстановление невозможно — понятная диагностика и ручной повтор, без зависшего окна.

Политика нагрузки: пользовательская пауза приоритетнее автоматического resume. При полноэкранном приложении на обслуживаемом мониторе приостанавливать стройку и снижать/останавливать рендер. При обычном окне поверх рабочего стола продолжать с ограничением FPS, если нет достоверного сигнала полного перекрытия. Не считать отсутствие фокуса поводом для паузы: у обоев фокуса обычно нет. При блокировке сеанса и сне приостанавливать; после возврата не накапливать delta и не проигрывать пропущенную стройку, а небо пересчитать по реальным часам. Пять секунд готовой пирамиды считать по активному видимому времени: на автоматической паузе сохранить остаток, чтобы финал не исчезал незаметно. Согласовать это явное уточнение с wallpaper.gd и тестом циклов. Звук всегда отключён.

Мультимониторный минимум: выбор целевого монитора, отдельная полная панорама на каждом включённом экране, без растягивания одной сцены через экраны разных пропорций. На W0 выбрать проверенную схему окон/рендеров; не вводить дорогую синхронизацию партий между экранами как обязательную функцию. Один host управляет всеми намеренно созданными рендерами — это не дубликаты запуска. Проверить отрицательные координаты виртуального рабочего стола, разные DPI/разрешения, смену основного монитора, подключение/отключение. При удалении выбранного монитора — явный переход на основной или пауза согласно настройке, без окна вне экрана. Полноэкранная пауза применяется к затронутому экрану.

**Готовность:** рабочие управление/выход/единственный host, восстановление Explorer и сна, политика паузы, управление мониторами и отсутствие осиротевших процессов. Непроверенные комбинации фиксируются отдельно; они не автоматически считаются поддержанными.

### W2. Автономный комплект и проверка поставки

**После T9.** Экспортировать Windows Desktop x64 комплект в отдельный каталог, предварительно build/wallpaper-standalone/. Один EXE не обязателен: предпочесть понятный набор host/renderer/ресурсов/лицензий, если объединение усложняет восстановление и подпись. Точный состав определить выбранной архитектурой W0. Godot runtime и все необходимые нативные зависимости входят в поставку; на целевом ПК не нужны редактор, Godot, SDK, Lively, Python или отдельно устанавливаемая среда выполнения. SDK допускается только на машине сборки. Проверить лицензии и способ распространения зависимостей.

Проверять именно этот экспорт из чистого каталога и на отдельной Windows x64 системе/VM без инструментов разработки. Проверка на текущем ПК с установленным Godot не доказывает автономность. VM подходит для зависимостей и входа/выхода, но не заменяет физическую проверку GPU, разных DPI и нескольких мониторов.

Составить таблицу «проверено / ошибка / не проверено» с версией Windows, оборудованием, шагами и результатом:

- старт без администратора и внешних программ, путь с пробелами/кириллицей;
- нахождение под значками и окнами, использование значков, Win+D, сворачивание/возврат приложений;
- полноэкранное приложение, пауза и возобновление, отсутствие рывка симуляции и правильное реальное небо;
- два цикла по 900 кирпичей и удержание результата, молчание, отсутствие игрового UI;
- мониторы с разными разрешениями/масштабированием, hotplug и смена основного;
- автозапуск после выхода/входа пользователя, задержка готовности Explorer, восстановление после его перезапуска;
- повторный запуск, штатный выход, сбой рендера/host, отсутствие лишних и зависших процессов;
- согласованная панорама без обрезки карьера, троса и вершины на реальном рабочем столе.

Перезапуск Explorer и выход из сеанса проверять в отдельной тестовой сессии/VM; не прерывать рабочий сеанс пользователя без согласования. Указать непроверенные варианты и безопасное поведение при неподдержанной оболочке. Не обещать обход предупреждений Windows о неподписанном приложении.

Обновить README: состав комплекта, главный файл запуска, настройки и выход, автозапуск/отключение, мониторы, удаление, расположение настроек/логов, команды сборки и поддержанные системы. Добавить результаты в PROGRESS и решения в DECISIONS. Старый Lively ZIP — исторический артефакт, не целевой выпуск; не удалять установленное стороннее ПО пользователя.

**Готовность:** автономный комплект и инструкция для другого ПК, доказанный запуск экспортированной версии на рабочем столе и честный перечень ограничений. Архив Lively больше не создаётся и не является критерием приёмки.

### Проверка целостности плана после замены платформы

- T0 остаётся исходной проверкой, W0 выполняется до окончательной компоновки T1.
- T1/T9 учитывают реальные мониторные размеры из W0/W1, а не только окно предпросмотра.
- T5 не зависит от Lively; обновляет небо после уведомлений собственного host. Контроллер неба продолжает жить независимо от сброса стройки.
- T8 сохраняет обычную игру и Android, но не переносит в них новые функции и не требует миграции сохранений.
- T9 проверяет содержимое и интеграцию, W2 — конкретный распространяемый комплект. Результаты переиспользуются; тесты повторяются при изменении кода/артефакта, а не для формальности.
- README и старые отчёты пока описывают реально существующую сборку. Они меняются на автономную инструкцию только после реализации, чтобы не заявлять несуществующую готовность.

Первичные источники для проверки Windows-адаптера на этапе реализации:

- SetParent и ограничения DPI: https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent
- DPI и взаимодействие окон: https://learn.microsoft.com/en-us/windows/win32/hidpi/high-dpi-desktop-application-development-on-windows
- TaskbarCreated и панель задач: https://learn.microsoft.com/en-us/windows/win32/shell/taskbar

Документация этих API не гарантирует стабильность неофициального способа использования WorkerW; совместимость подтверждается отдельно экспериментом W0 и матрицей W2.
